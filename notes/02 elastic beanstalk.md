## Elastic Beanstalk (EB) - Architecture

- EB = PaaS (platform as a service) -- vendor handles all infrastructure, you manage the code
- EB = developer-focused product
    - user provides app code & EB handles the environment/infrastructure
        - EB provisions these resources in your account! You can go in and see them under their respective resources
    - good for small developer teams, getting POCs up and running
    - fully customizable. Uses AWS products and services
- Platforms (and languages)
    - Built-in and natively supported platforms
        - Go, Java SE, Tomcat
        - .NET Core (Linux and Windows)
        - Node.js, PHP, Python, Ruby
    - Docker
        - multi-container mode uses ECS behind the scenes        
        - single container Docker
        - multi-container Docker
        - preconfigured Docker
            - way EB supports things before they're natively supported by EB
    - Custom Platforms
        - custom via Packer
- Terminology
    - Elastic Beanstalk Application = a collection of things relating to an application -- more of a container/folder 
    - Application Versions = specific labeled version of deployable code for an application. 
    - Source bundle = ZIP files/WAR files that hold an application version 
        - source bundle = indicator referring to beanstalk 
    - Environments = containers of infrastructure and configuration for a specific application version
        - subcontainer inside the Application container
        - environments actually contain the infrastructure
        - each environment is either a web server tier or a worker tier
        - web server tier = communicate with end users
            - accept traffic from end users 
        - worker tier = process work from the web tiers
- Architecture
    - application = top-level container
    - environment = container inside application 
        - 2 types of environments: web and worker
            - web and worker tiers communicate via SQS queues. worker tiers scale based on queue messages
        - each environment has an Auto Scaling group
            - web tier accepts connections from customers via an Elastic Load Balancer (ELB)
            - any workloads generated by the web server tier are passed into an SQS queue as messages. 
            - worker tier receives messages from the SQS queue. worker tier scales based on number of messages in the SQS queue.
            - web tier scales based on incoming requests to its load balancers
- Summary
    - not free! must tweak app to get it to work with EB
    - great for small dev teams 
    - use Docker for any platforms not supported natively by EB
    - (almost) always provision and maintain DBs OUTSIDE of EB !!
        - you can point EB at DBs outside of EB
        - you can technically create DBs inside EB
            - but the DB would be lost if the environment is deleted

## Elastic Beanstalk (EB) - Deployment Policies
- All at once = deploy to all instances at once, brief outage
    - good for test envs
- Rolling = deploy in rolling batches
    - batch size can be customized >= 1 (base this on how many instances you can tolerate being offline at one time)
    - waits for current batch to finish, health checks to pass before moving to next batch
    - loss in capacity because instances are removed from service while the deployment is happening (instances removed from service, upgraded, then returned to service)
    - 2 versions running at same time
- Rolling with additional batch = as above, with extra batch to maintain capacity during process
    - better for production, customers won't see any drop in capacity. 
    - 2 versions running at same time
    - takes longer, costs more, but safer. 
- Immutable = all new instances with new version 
    - new temp ASG created with new instances running new app version
    - once instances pass health check, moved to original ASG, and original instances terminated, then temp ASG removed
    - high cost because uses double the instances, but easiest to roll back because the original instances are untouched until deployment is complete
- Traffic splitting = fresh instances, with a traffic split
    - same idea as immutable, but adds traffic splitting between old and temp ASG
    - new temp ASG created, instances created inside it with new version, but you can control distribution of traffic between old and new version.
    - allows for A/B testing of versions
    - no capacity drops
- Blue/green
    - one environment with version A, separate environment with version B, running in parallel. Can do testing in offline environment before switching DNS to new active stack. Can keep secondary env running as long as you want
    - DNS record can be adjusted to switch environments. Simple rollbacks



## Elastic Beanstalk (EB) - Environments and RDS
- you CAN create an RDS instance within an EB environment, but then if you delete the environment, bye bye DB. Also, different EB environments = different DB = different data 
    - environment properties you can access if you make the instance within EB:
        - RDS_HOSTNAME, RDS_PORT, RDS_DB_NAME, RDS_USERNAME, RDS_PASSWORD
        - any application code running within the env can use these properties to get the info
- you can create an RDS instance outside EB
    - you'll have to manually create the environment properties to point at your RDS instance
        - RDS_HOSTNAME, RDS_PORT, RDS_DB_NAME, RDS_USERNAME, RDS_PASSWORD
    - environments can be swapped out at will -- data is outside the lifecycle of the EB environment
- decoupling RDS created within EB from the EB environment
    1. create RDS snapshot 
    2. enable deletion protection
    3. create new EB environment with same app version
    4. ensure new environment can connect to existing DB
        - verify environment properties, security groups, etc are all correct
    5. swap environments (CNAME or DNS)
    6. now NEW env pointing at existing RDS instance
    7. terminate the old environment -- this will TRY to terminate the RDS instance since their lifecycles are linked, but since we have deletion protection, this won't be possible.
    8. old environment gets removed, but not the RDS instance
    9. go to CloudFormation, look for DELETE_FAILED stack, manually delete the stack and choose to retain stuck resources
    10. now your RDS instance is decoupled from the EB environment it was in!

## Elastic Beanstalk (EB) - Advanced Customisation via .ebextensions
- EB uses CloudFormation to provision infrastructure!!!
    - you can go in and see the stacks
- `.ebextensions` are a way to customize EB environments
    - add `.ebextensions` folder inside the app source bundle (ZIP or WAR)
    - in that folder, files ending in `.config` will be treated as `.ebextensions` config files
    - these files use CloudFormation format to create additional resources within that environment
- `.ebextensions` configuration elements inside these `.config` files
    - `option_settings` -> allows you to set options of resources
    - `Resources` -> allows creation of entirely new resources
    - (also introduced in CFN-INIT:) `packages`, `sources`, `files`, `users`, `groups`, `container_commands`, `services` 


## Elastic Beanstalk (EB) - HTTPS
- In order to use HTTPS with EB, you must:
    1. Apply SSL certificate to the load balancer
        - manually in console or via `.ebextensions`:
            - EB console -> environment -> load balancer configuration
            - `.ebextensions/securelistener-[alb|nlb].config` -- Open question: do `.ebextensions` files have specific name requirements?
    2. Configure the security group (manually or via `.ebextensions`)
        1. allow port 443 to access the load balancer
        2. allow load balancer to connect to the instances on the relevant ports


## Elastic Beanstalk (EB) - Cloning
- use cases: copy prod env to a test env, or new version of a platform branch
- copies options, env vars, resources, other settings
- makes copies of resources associated with the EB env
    - will copy any RDS in the ENV, BUT DATA IS NOT COPIED
        - you'll need to migrate the data yourself afterwards
- can't make any changes during the copy!! (so you may need to make updates afterwards)
    - EXCEPTIONS -- when you select clone, you can modify
        - environment name
        - environment URL
        - description
        - platform version (NOT platform branch) -- Open question: what's the difference?
        - service role used for this env
- you can only clone an env to a different platform version of the same platform branch
    - a different platform branch isn't guaranteed to be compatible
    - to use a different platform branch
        1. manually create new env
        2. deploy app code
        3. make any necessary changes in code to ensure it functions correctly
- NOT copied
    - data in RDS
    - unmanaged changes
        - changes you make to infra using any tools other than the EB console/CLI/API (like manually modifying an EC2 instance)

## Elastic Beanstalk (EB) - Docker
- single container (creates container in single EC2 instance)
    - referred to as "Docker" in console UI
    - can only run 1 container on 1 Docker host
    - uses EC2 NOT ECS
    - you have to provide at least one extra configuration piece:
        1. `Dockerfile` -> EB will build a Docker image and use this to run a container
            - use this option if you want to cleanly build a container within EB
        2. `Dockerrun.aws.json` (version 1) -> use an existing Docker image -- configures image, ports, volumes, and other Docker attributes.
        3. `docker-compose.yml` -> if you use Docker Compose
- multi-container Docker mode (creates ECS cluster)
    - multiple containers per EC2 instance
    - EB uses ECS to create an ECS cluster, and then within this, EC2 instances are provisioned in the cluster, as well as an ELB for high availability
    - you need to provide `Dockerrun.aws.json` (version 2) file in the application source bundle (root level)
    - any images used need to be stored in a container registry (like ECR)
